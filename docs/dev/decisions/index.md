# Architectural Decisions

> **Authority:** this index lists **decisions** — why a boundary exists. Current
> obligations live in [contracts/](../../contracts/index.md); evidence in
> [research/](../research/index.md). A decision never replaces the contract that
> operationalizes it, and long summaries below are historical records of the
> decision text, not restatements of the current rules.

| ADR | Status | Decision |
|---|---|---|
| ADR-0001 | Accepted | Use the generated golden-path baseline and grow infrastructure only when requirements justify it. |
| ADR-0002 | Accepted | The semantic engineering model is the product core; all consumers depend on it. |
| ADR-0003 | Accepted | Keep semantic engineering data and presentation/rendering data strictly separate. |
| ADR-0004 | Accepted | YAML is a serialization format validated into the domain model, not the domain model itself. |
| ADR-0005 | Accepted | Use `ProcessModel` as the process-graph container and S1–S4 validation boundary while `PlantModel` remains the overall aggregate. |
| ADR-0006 | Accepted | Accept `PlantModel.process: ProcessModel \| None` as the first root shape and the YAML `process` section as the first serialization boundary. |
| ADR-0007 | Accepted | Do not redistribute restricted standards content; reference normative standards by identifier with human verification; allow AI agents only openly licensed standards material, DeepPlant-authored summaries, and public material whose applicable terms explicitly permit AI use; require explicit redistributable provenance for all distributed symbol assets; treat standards correspondence and asset copyright as separate concerns; use DEXPI under CC BY 4.0 with attribution without making it the drawing standard. |
| ADR-0008 | Accepted, partially superseded by ADR-0009 (only the `ProcessStep.type` → symbol-role coupling) | Use SVG as the initial presentation asset format for the process/PFD layer: a symbol role (in the original text read from `ProcessStep.type`) is not globally canonical SVG geometry; a future presentation layer selects a graphical symbol pack; the initial DeepPlant-original `basic` pack is non-normative fallback/reference geometry under `assets/symbols/process/basic/` with uniform `viewBox="0 0 100 100"` and machine-readable ordered `anchor-in-N` / `anchor-out-N` slots distinct from semantic `ProcessPort` ids; input/output roles derived from `ProcessStream` incidence; anchors are hidden via `fill`/`stroke="none"` without an exact radius, unrelated internal SVG ids allowed; pack selection, renderer, layout, routing, labels, rotation, and custom-pack machinery deferred. The role → pack → SVG + anchor contract remains in force. |
| ADR-0009 | Accepted | Separate `ProcessStep.function` (open, DeepPlant-native engineering semantics) from the presentation symbol role (resolved by renderer presentation policy or explicit per-step overrides at the rendering boundary; never stored in the semantic model); remove `ProcessStep.type` as an intentional pre-1.0 break; `unspecified` remains a legal function; unresolved-role rendering is a presentation error; DEXPI maps step classes onto DeepPlant functions (including reverse material-only `pumping`); persistent view configuration deferred. |
| ADR-0010 | Accepted | Keep the DEXPI Plant/P&ID semantic boundary at the current primitives: `Port` remains the canonical physical connection point (a documented collapse of DEXPI `Nozzle` + `PipingNode`; no `Nozzle` concept), `Connection` remains directed semantic topology only (never a pipe, pipe segment, piping line, process stream, signal, or cable), piping realization (`Pipe`, `PipingNetworkSegment`, `PipingNetworkSystem.LineNumber`, piping class, fluid code, nominal diameter) and the instrumentation/signal function layer are recognized as separate future layers that depend on their own evidence and Issue, Plant/P&ID import stays unimplemented and fail-closed, and DEXPI `Core.Diagram`/`Plant.Diagram` constructs stay presentation-only. The physical-piping-layer design this ADR deferred is now specified and decided by [ADR-0011](ADR-0011-canonical-physical-piping-realization.md). |
| ADR-0011 | Accepted | Represent physical piping as `PipingLine` → `PipingSegment` → `PipingRealization` inside an optional `PipingModel` container (`PlantModel.piping`), referencing identified `Connection`s: `Connection` stays pure directed physical adjacency and gains only canonical identity (`Connection.id`, required, non-empty, plant-unique, a documented pre-1.0 breaking change to authored YAML); the piping layer never restates topology, so piping is a dependent cross-layer-validated submodel rather than an independent graph; `PipingLine` carries canonical `id` plus optional human `line_number`/`name`; `PipingSegment` carries owner-local canonical `id` plus optional human/external `segment_number` (DEXPI `SegmentNumber` maps here, while neither it nor XML `Object@id` becomes canonical), and segment properties; first-slice segment boundaries must align with `Connection` boundaries, so mid-connection DEXPI `PropertyBreak` semantics are explicitly deferred; `PipingRealization.kind` is closed to `pipe | direct` (default `pipe`, invalid values fail validation; no realization remains distinct from `pipe`); no canonical `Pipe` or `DirectPipingConnection` class; inline components remain `Equipment`; `Port` remains the endpoint with no `Nozzle`/`PipingNode` refinement; C1 plus P1–P5 apply, with P4 an intentionally conservative first-slice 1:1 invariant that requires later evidence to relax; no presentation, process, or instrumentation data enters the layer, and Process ↔ physical realization remains explicitly undecided. Specification: [docs/dev/research/physical-piping-model.md](../research/physical-piping-model.md) |
| ADR-0012 | Accepted | Canonical `ProcessStep` currently has exactly one classification axis, `function`: no generic second canonical process-step classification is justified and no name for one is reserved, because DEXPI's nine `Method` properties across seven enumeration domains are not one reusable engineering concept — their value domains are heterogeneous, mixing mechanism/principle labels, equipment technology or construction, and non-answers inside single enums. Many literals have direct or close counterparts in `Plant.ProcessEquipment`, demonstrating overlap with physical realization rather than universal ownership; the inventory does not expose one reusable cross-cutting `ProcessStep` concept. A generic second classification (B) and a function-specific details structure (C) are rejected now; Candidate D is a plausible future home for part of the vocabulary, not an implementation decision. `ProcessStep.function` stays an open non-empty string (ADR-0009 preserved), no `realized_by`/Process ↔ physical mapping is introduced, no generic property/attribute/metadata bag, generic `Property`/`Attribute`/`Entity`, generic schema framework, or unioned `ProcessStepMethod` enum is introduced, adapter round-trip convenience is not a justification for canonical growth, and adapter `Method` support stays explicitly unsupported where DEXPI requires it. Evidence: [docs/dev/research/process-step-classification.md](../research/process-step-classification.md) |
| ADR-0013 | Accepted | The canonical model needs a reusable qualified-engineering **value** — a stored scalar magnitude plus represented engineering-unit semantics — owned by explicit, domain-specific physical-quantity properties (`duty`, `head`, `temperature`, `design_pressure`, `wall_thickness`, `outside_diameter`): the value representation is generic and cross-cutting and belongs in the semantic model, while property name/meaning stays domain-owned and is never replaced by generic string keys; a generic property/parameter bag is rejected (ADR-0012 reasoning) and per-property quantity classes (`PressureQuantity`, `TemperatureQuantity`, …) are rejected now; units are stored canonical state, not presentation; DeepPlant preserves stored magnitude and represented unit, so `10 bar` and `1 MPa` are distinct canonical representations under canonical-state equality, while they may be physically equivalent through deferred unit-aware comparison/conversion; DEXPI schema evidence establishes explicit magnitude and typed unit fields but not producer normalization or authoring provenance; current `PipingSegment.nominal_diameter` remains a nominal designation/string-like property outside this decision; the adapter translates external quantity representations (for example DEXPI `QualifiedValue`/`PhysicalQuantity`) into the canonical value and back when a future mapping is implemented; only scalar values are in scope, with richer value semantics (vectors, numeric ranges, uncertainty/tolerance, `float` vs exact decimal) and DEXPI `0..*` multiplicity mapping deferred; nothing is implemented by the decision and `ExchangingThermalEnergy` is **not** made supported. Evidence: [docs/dev/research/qualified-engineering-quantities.md](../research/qualified-engineering-quantities.md) |
| ADR-0014 | Accepted; physical-ownership interpretation superseded by [ADR-0015](ADR-0015-documentation-architecture-v2-1.md) | Treat **audience navigation** and **knowledge authority** as independent documentation dimensions and adopt a **hybrid** structure: a shared canonical layer (`docs/contracts/`, root-level current/policy documents, `project/brief.md`) keeps cross-audience truth, while `docs/user/` and `docs/dev/` hold only genuinely audience-specific navigation or guidance; a canonical document relevant to several audiences stays in the shared layer and is linked from both audience indexes. Filesystem location is **not** the only audience signal (navigation indexes and `read_when` are primary; deliberately **no `audience:` metadata field**). Conceptual atomicity — "one document primarily owns one durable concept, workflow, task, or question" — is the decomposition rule, and numeric line counts are a review signal, not architectural validity (no hard limits; one 120-line soft signal retained only for navigation/entry documents because router value decays with size). Stable paths are kept by default, with explicit KEEP/MOVE/SPLIT criteria and a link-reconciliation procedure for moves (repository-internal links, indexes/navigation, front-matter references, `README.md`/`AGENTS.md`, link validation, one canonical copy; redirect stubs only for a demonstrated external-compatibility need). Markdown stays canonical and no renderer is introduced. Operational rules: [docs/dev/workflow/conventions.md](../workflow/conventions.md); migration inventory and sequence: [docs/dev/workflow/documentation-migration.md](../workflow/documentation-migration.md) |
| ADR-0016 | Accepted | Future process ↔ physical realization relationships belong in a separate cross-layer realization layer, never on `ProcessStep`/`ProcessStream`/`ProcessPort` or on `Equipment`/`Port`/`Connection`/`PipingRealization`/`PipingSegment`/`PipingLine`. The process, physical-topology, and piping models stay independently valid: neither side requires the other, and zero relationship participation must be valid in both endpoint directions, while future `1:N`/`N:1`/`N:M` cases must not be precluded (but are not encoded). A `ProcessStream` realization targets a physical route / collection of existing realization facts, not one `Connection`, `PipingRealization`, `PipingSegment`, or `PipingLine`. Step/equipment and stream/route are domain-specific relation kinds, not one forced symmetric schema. No mapping field/class, YAML, validator, relation identity, metadata, port refinement (`Nozzle`/`PipingNode`), or runtime behavior is introduced. Evidence: [docs/dev/research/process-physical-realization-boundary.md](../research/process-physical-realization-boundary.md) |
| ADR-0015 | Accepted | Refine Documentation Architecture v2 to **v2.1**: retain `audience != knowledge authority` and add **`canonical != shared-directory`**. Authority decides the kind of truth; audience decides who primarily needs it; location follows audience unless content is genuinely cross-audience. `docs/contracts/**` holds only cross-audience contracts; developer-only contracts/reference live under `docs/dev/reference/`. Thus `rendering.md` moves to `docs/contracts/`, while `dexpi-process-adapter.md` and `svg-symbols.md` move to `docs/dev/reference/`. Architecture, workflow/governance, planning, decisions, research/evidence, and history are developer/agent-owned canonical content under `docs/dev/**`; `docs/user/**` owns how-to-use guidance. `README.md`, `VISION.md`, `AGENTS.md`, and `project/brief.md` are repository-role exceptions, not shared solely because of location; `docs/index.md` is global navigation. The inventory also records `product.md` as internal planning and a future user-facing `what-is-deepplant.md` replacement. It supersedes ADR-0014's physical-ownership interpretation only. Operational rules: [docs/dev/workflow/conventions.md](../workflow/conventions.md) |
